# 為什麼做這個專案（晏銘湛箴_無用之用）

## 無用之用：三十輻共一轂，當其無，有車之用

老子《道德經》第十一章：「三十輻共一轂，當其無，有車之用。」

把這個比喻套進 Agent：

- **轂（車軸中心）= Agent 本體**：本身是空的，不攜帶任何業務能力。
- **輻（輻條）= Skill**：可換、可增減、可動態增刪。

「無用之用」的意思在於轂的空——正因為 Agent 本體不寫死任何業務技能，它才能隨時換上不同的 skill。本倉庫（`wuyong`）不內置任何業務 skill，只內置「找 skill、管 skill 池」的能力。

## 刪除你的 skill！

目前的 Agent 框架越來越新，寫死的靜態工具會過期。今天的「最佳實踐」明天就可能過時。Skill 池不應該是手寫清單，而應該是**派生物**：

> Skill 池 = skills.sh 排行榜（按調用量由上往下取） + 本地製作歷史（跨對話共用）。

動態算出，而不是靜態維護。

## 用戶輸入 × 模型思考：底層邏輯

大多數 Agent 只看「用戶說了什麼」。但模型自己在思考時，常會意識到能力缺口（例如「也許有現成的 skill」、「我不確定怎麼做 X」）。把「用戶說了什麼」與「模型想了什麼（Thinking/Reasoning Trace）」結合起來判斷需求，這本身就是本專案的底層邏輯。

- 用戶文字通道：中英文句式與關鍵詞（「怎麼做」「有沒有現成的」「幫我做 X」…）。
- 模型思考通道：思考路徑中出現使用 skill 的可能性。
- 兩個通道分別判別，再合併；規則層為預設，LLM 判官可選、預設關閉、不得成為必需。

## 要解決的困境：用戶缺的不是 skill，是品牌規範與審美優化

高品質 skill 一般人寫不出來。用戶真正缺的，不是「某個 skill」，而是「什麼時候該用哪個高品質 skill」的規範與審美優化。所以 skill 池要動態地從 skills.sh 由上往下按調用量取，把被社群驗證過的高頻 skill 優先呈現。

## 這是第一個「被動檢測」子 agent

定位：常駐 sub-agent，不只緘默觀察，識別到需求後會直接幹活。

- 負責監控池子，並告訴主 agent「這件事該怎麼做、該用哪個能力」。
- 這點最重要，必須寫進 System Prompt 與 README。

## 設計上如何體現

| 原則 | 在程式碼中的體現 |
|------|-----------------|
| 不內建業務 skill | `src/wuyong/` 只包含路由、監控、索引、安全閘；`skills/core/`、`skills/pool/` 空（runtime 生成） |
| Skill 池是派生物 | `monitor/skills_sh.py` 從 skills.sh API/HTML 快取排行榜；`pool.py` 動態建立池記錄 |
| 用戶 × 思考雙通道 | `signals/detector.py` 分別掃描 `user_text` 與 `thinking`，再合併分數 |
| 跨對話命中 | `registry/local_index.py` 記錄 `origin_conversation_id`、`created_at`、`path`、`hash` |
| 不編造安裝量 | 所有 installs 來自 skills.sh；取不到如實標記 `stale` / `degraded` |
| 零遙測、純本地 | `DISABLE_TELEMETRY=1`；不改註冊表；用戶文字與思考內容不外傳 |
